## Script 01 — BPE Tokenizer from Scratch

### What is BPE?

**Byte Pair Encoding** is the tokenization algorithm used by GPT-2, GPT-4, Llama, and most modern LLMs. It was originally a data compression technique. The core idea: *find the most frequent pair of adjacent symbols and merge them into one*.

### Why tokenization matters

A model never sees text. It sees a list of integers. The tokenizer is the translator between human language and model input. Every design choice in the tokenizer — vocabulary size, training corpus, number of merges — permanently shapes what the model can and cannot represent efficiently.

### Step-by-step: what the code does

**Step 1: Character initialization**

Every word in the corpus is split into individual characters, with a special `</w>` marker appended:

```
"cat"  →  ('c', 'a', 't', '</w>')
"the"  →  ('t', 'h', 'e', '</w>')
```

The `</w>` marker is crucial. Without it, the tokenizer cannot tell whether `est` appears at the *end* of a word (like `fastest</w>`) or *inside* a word (like `estimate`). These should produce different tokens because they carry different positional meaning.

**Step 2: Count adjacent pair frequencies**

The algorithm scans every word and counts every adjacent pair of symbols:

```
('c','a','t','</w>')  →  pairs: (c,a)=1, (a,t)=1, (t,</w>)=1
('t','h','e','</w>')  →  pairs: (t,h)=1, (h,e)=1, (e,</w>)=1
```

If many words share a pair (e.g. `t,h` appears in "the", "that", "this", "they"), that pair will have a high frequency.

**Step 3: Merge the most frequent pair**

The highest-frequency pair is merged into a single symbol everywhere it appears:

```
(t, h) → "th"
('t','h','e','</w>')  now becomes  ('th','e','</w>')
```

This is the entire algorithm. Repeat for `NUM_MERGES` iterations.

**Step 4: Build the vocabulary**

After all merges, every unique symbol that ever appeared is the vocabulary. Early merges create frequent subwords (`th`, `ing`, `er`). Late merges create rare combinations.

### What to observe when you change things

| Change | What happens | Why |
|--------|-------------|-----|
| `NUM_MERGES = 5` | "cat" stays as `c a t </w>` — 4 tokens | Too few merges, no subwords formed |
| `NUM_MERGES = 100` | "cat" becomes `cat</w>` — 1 token | Common words get fully merged |
| Add domain text (e.g. Python code) | `def`, `return`, `self` become single tokens early | They appear so often the pair frequencies dominate |
| Add Kannada/Hindi text | Token count explodes for those words | Script never seen in training — every character stays split |
| Repeat one word 50x | That word's subwords get merged before others | Artificial frequency inflation — same problem as biased training data |

### The output: merge rules

The script saves `merge_rules.json` — an ordered list of all merge operations. This ordering matters. When you tokenize new text, you apply the same merges in the same order. A pair that wasn't merged during training (because it wasn't frequent enough) will never be merged during inference either. This is why out-of-vocabulary words get fragmented into characters.

## Script 02 — Embedding Explorer

### What is an embedding?

An embedding is a dense vector of floating-point numbers that represents the *meaning* of a piece of text. The key property: **semantically similar texts have vectors that point in similar directions.**

A 384-dimensional embedding means each sentence is a point in 384-dimensional space. You cannot visualize 384 dimensions, but you can compute distances and angles between points — and those distances encode semantic relationships.

### The model: `all-MiniLM-L6-v2`

This is a 22M parameter model from the SentenceTransformers library. It is:
- Small enough to run on CPU in under a second per sentence
- Good enough to produce meaningful embeddings for most tasks
- A distilled version of a BERT-family model

The `L6` means 6 transformer layers. `MiniLM` means it was distilled from a larger model using knowledge distillation. The `all-` prefix means it was trained on a broad dataset of 1 billion sentence pairs.

### Cosine similarity — the core metric

Two embeddings are compared using **cosine similarity**:

```
cosine_similarity(A, B) = (A · B) / (|A| × |B|)
```

This measures the *angle* between two vectors, not their distance. Why angle and not distance? Because the *magnitude* of an embedding is not meaningful — only its direction is. Two embeddings pointing in the same direction are semantically similar regardless of how long the vectors are.

Score interpretation:
- `1.0` → identical meaning
- `0.8+` → very similar (paraphrases)
- `0.5–0.7` → related topic
- `0.3–0.5` → loosely related
- `< 0.3` → unrelated

### The four experiments in script 02

**Experiment A: Similarity matrix**

Every sentence is compared against every other sentence. This is an N×N matrix where each cell `(i,j)` is `cosine_sim(sentence_i, sentence_j)`.

The critical observation: the two "bank" sentences:
- `"The bank was flooded with complaints"` → lands near abstract/institution sentences
- `"She sat by the river bank"` → lands near nature/location sentences

Same word, different vector position. This is **contextualized embedding** — the model encodes the meaning of the entire sentence, not just individual words.

**Experiment B: Vector arithmetic**

The famous `king - man + woman ≈ queen` relationship works because:

If the model has learned that "king" and "queen" differ along a "gender" axis, and "man" and "woman" differ along the same axis, then subtracting the man-direction and adding the woman-direction to "king" should land you near "queen".

```
direction(royalty + male) - direction(male) + direction(female)
= direction(royalty + female)
= "queen"
```

This works well for relationships the model was trained on. It breaks for relationships that weren't explicitly in the training data — notice what happens with the pasta/Python analogy.

**Experiment C: Context shift**

The naked word `"bank"` is ambiguous. With a financial sentence, it shifts toward the financial region of vector space. With a river sentence, it shifts geographic. This is the fundamental difference between:

- **Word2Vec**: one fixed vector per word regardless of context
- **SentenceTransformers/BERT**: vector changes based on surrounding words

**Experiment D: PCA projection**

PCA (Principal Component Analysis) finds the two directions in 384-dimensional space that capture the most variance, then projects all points onto those two directions. This lets you visualize the embedding space as a 2D scatter plot.

The "variance explained" percentage (shown in the visualizer) tells you how much information was lost in projection. If it says 38%, that means 62% of the information is invisible in the 2D view. The clusters you see are real, but the distances between clusters are distorted.

## Script 03 — Similarity Experiments

### Experiment 1: Semantic drift chain

Starting at one word, we repeatedly hop to the nearest neighbor. After 8 hops, we're usually very far from where we started — but every individual hop was locally reasonable.

This is directly relevant to RAG: if your retrieval uses approximate nearest neighbor search, it can return results that are one plausible hop away from what you actually wanted. In a long pipeline, these small errors compound.

### Experiment 2: Negation blindspot

This is one of the most important failure modes to internalize.

`"I am happy"` and `"I am not happy"` will often have cosine similarity above 0.85.

Why? Because SentenceTransformers are trained on semantic similarity tasks where the goal is to group related content together. Negation is subtle — the word "not" is a small token in a sea of content-bearing words. The model encodes that both sentences are *about* happiness, and the negation signal gets diluted.

Practical consequence: if you build a RAG system over a policy document that says "do NOT store customer PII in logs", a query about storing PII may retrieve that sentence and the LLM may misread the retrieved context. Cross-encoder rerankers are better at catching negation because they see the query and document together, not independently.

### Experiment 3: Length vs quality

Adding more context around the same core meaning generally increases similarity to a semantically similar query — up to a point. Very long sentences can dilute the signal because the fixed-size embedding vector (384 dimensions) must now compress more information.

This is why RAG chunk size is a real hyperparameter. Too small: not enough context to disambiguate meaning. Too large: the specific relevant content gets diluted by surrounding noise.

### Experiment 4: Cross-language similarity

`all-MiniLM-L6-v2` was trained on multilingual data. The same sentence in Hindi, Kannada, French, and German should embed close to the English original — because the model learns to map meaning, not surface form.

Notice that Kannada and Hindi may score lower than French/German. This reflects the distribution of the training data: Indo-European languages (French, German, Spanish) were more represented than Dravidian languages (Kannada, Tamil, Telugu).

This has direct implications: if you're building a RAG system that needs to handle Kannada user queries over English documents, you need to either (a) use a better multilingual model, or (b) translate queries before embedding.

### Experiment 5: Hubness

In high-dimensional spaces, some vectors become "hubs" — they appear as the nearest neighbor of many other vectors, even when they're not truly the most relevant match. This is a mathematical property of high-dimensional geometry called the **curse of dimensionality**.

In a retrieval system, a hub document would be returned for many different queries, crowding out more specific but accurate results. This is why diversity-aware retrieval strategies (like Maximum Marginal Relevance) exist.

## Key mental models to take away

**1. Tokenization is compression, not splitting**
BPE doesn't "split words at syllables." It merges the most statistically frequent character pairs. The result is a vocabulary that efficiently represents the training corpus — and is inefficient for everything else.

**2. Embeddings encode direction, not magnitude**
Two embedding vectors pointing in the same direction are semantically similar even if one is twice as long. This is why cosine similarity (angle) is used, not Euclidean distance (length).

**3. Context changes the vector**
The same word embedded in different sentences lands in different positions. There is no single vector for "bank." There is a vector for "bank as used in this particular sentence."

**4. Similarity ≠ correctness**
High cosine similarity means the model thinks two texts are semantically related. It does not mean one is a correct answer to the other. A sentence about "not taking the medication" is semantically similar to "taking the medication" — both are about the same topic.

**5. Dimensionality reduction loses information**
The 2D PCA map is a shadow of a 384-dimensional object. The clusters are real. The exact distances between clusters are not. Never make quantitative claims about distance based on a PCA plot.
